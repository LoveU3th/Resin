# Resin v1.3.1 优化方案：劣质节点池下的首跳质量

本文档记录 v1.3.1 的目标、改动项、验收标准与实施进度。
It records the goals, changes, acceptance criteria and progress of v1.3.1.

## 1. 背景与基线

v1.3.0 上线后，在生产池（506 个节点、约 48% 未熔断）上连续观测 12 小时，
与调整前的 12 小时对比：

| 指标 | 调整前 | 调整后（v1.3.0 + 配置） |
|---|---|---|
| 请求成功率 | 90.0% | 93.7% |
| 首字节 p50 | 1168ms | 1181ms |
| 首字节 p90 | 2996ms | 3206ms |
| 首字节 p99 | 6067ms | 4710ms |
| >5s 慢请求 | 6.0 次/时 | 2.1 次/时 |
| >10s 慢请求 | 0.41% | 0.13% |
| 首跳成功率 | 58% | 60% |

结论：容器级超时与探测并发（拨号 3s、TLS 5s、`probe_concurrency=200`）
把尾部压下来了，但**首跳成功率只从 58% 到 60%**，说明问题在选点质量，
不在超时。失败构成也印证了这一点：`connect_no_ingress_traffic`
（节点接受 CONNECT 后不返回数据）占全部失败的 70%。

### 根因分析

1. **P2C 的延迟比较在真实流量上几乎总是退化。**
   `compareLatencies` 只在两个节点都有同一 target/authority 的样本时才返回延迟，
   否则返回 `(0, 0)`。用户目标域名不可能同时命中两个节点的延迟表，
   于是 `calculateScore` 走 `latency <= 0` 分支，分数退化为「租约数」——
   选点变成按负载随机挑选，节点质量完全不参与。
2. **固定 k=2 在健康率 48% 的池子里上限只有 73%**
   （`1 - 0.52²`），实际受节点质量限制停在 60%。
3. **隧道流量不进访问延迟直方图。**
   `Collector.RecordRequest` 对 `isConnect=true` 直接跳过延迟记录，
   而本部署 99.9% 是 CONNECT 隧道，导致 `/metrics/history/access-latency`
   26 小时只有 20 个样本，评估只能翻请求日志。

## 2. 验收目标

| 指标 | 现状 | v1.3.1 目标 |
|---|---|---|
| 首跳成功率 | 60% | ≥ 67% |
| 请求失败率 | 6.3% | ≤ 5% |
| 首字节 p99 | 4.71s | ≤ 4.5s |
| >5s 慢请求占比 | 0.44% | ≤ 0.3% |

## 3. 改动清单

### P0-1 修复 P2C 延迟比较退化

- `internal/routing/latency_eval.go`：新增 `nodeLatency`（target → 单节点 authority 均值），
  `compareLatencies` 在交集失败后逐节点兜底，而不是直接返回 `(0, 0)`。
- `internal/routing/random.go`：`calculateScore` 对未知延迟使用冷启动常数
  `coldStartLatency = 400ms`，不再让「没测过」等同于「零延迟」；
  `PreferIdleIP` 策略保持只按租约计分。
- 预期：首跳 +5~7pp。

### P0-2 P2C 候选数自适应

- `internal/routing/random.go`：选点宽度从固定 2 改为按池子可接受率自适应
  （<35% 用 4，<60% 用 3，其余 2），上限 4；按可接受率抽样（上限 32 个候选）估算。
- 选择仍用两两比较归约，复用 `compareLatencies` / `calculateScore`，
  不引入第二套评分路径。
- 预期：首跳 +3~5pp。

### P1-1 零入向隧道快速隔离

- 数据：`connect_no_ingress_traffic` 占失败 70%，当前要连错 3 次才熔断。
- 方案：per-node `noIngressStreak`，连续 2 次零入向即软隔离 5 分钟
  （不进熔断状态机，只在 `HealthWeights.allows` 拒绝），成功一次清零。

### P1-2 收窄故障转移总预算

- `failover_total_budget` 默认 90s → 20s（实际最差路径 4 × 3s = 12s）。

### P0-3 补齐隧道延迟观测

- CONNECT 隧道按 `first_byte_duration_ms` 记入独立直方图，
  API 加 `include_tunnel` 参数，默认关闭保持兼容。

### P2 默认值对齐

| 项 | 现值 | 建议 |
|---|---|---|
| `health_filter_threshold_percent` | 40 | 50 |
| `health_min_samples_for_filter` | 8 | 4 |
| `failover_total_budget` | 90s | 20s |

### P1-2 为何不实施

计划里写的是把 `failover_total_budget` 从 90s 降到 20s，但代码里有一条硬约束：

```
failover_attempt_budget must not exceed failover_total_budget
```

而 `failover_attempt_budget` 的注释明确要求它不得短于 `ResponseHeaderTimeout`
（默认 60s，见 `RESIN_PROXY_TRANSPORT_RESPONSE_HEADER_TIMEOUT`），否则「慢但健康」
的上游会在回答前被放弃。两者相加意味着总预算至少要 60s 量级，20s 无法成立。

另外，实测的 12s 尾部来自**连接超时 × 尝试次数**（4 × 3s），不是总预算造成的；
13.6 小时里只有 8 次超过 10s。为一个几乎不出现的场景去破坏慢上游的保护，不划算。

如果确实要收紧，正确顺序是：先降 `RESIN_PROXY_TRANSPORT_RESPONSE_HEADER_TIMEOUT`，
再同步降 `failover_attempt_budget`，最后才是 `failover_total_budget`。

### P0-3 为何暂缓

`access-latency` 直方图当前量程是 0–3s（超出进 overflow 桶），而隧道首字节 p99 实测
约 3.6s——直接把隧道首字节塞进去，会有相当比例的样本落到 overflow，分位数反而失真。
正确做法是先调整 `latency_bin_ms` / `latency_overflow_ms` 这两项指标参数，
再决定是否把隧道流量并入同一张表。这属于指标侧的独立变更，不和路由改动混在一个版本里。

同时确认了一个对 P0-1 有利的事实：CONNECT 隧道在 TLS 握手完成时已经通过
`RecordPassiveLatency` 把**真实目标域名**的延迟写入节点延迟表
（`internal/proxy/tunnel.go` 的 `newTLSLatencyConn` 回调）。因此 P0-1 的逐节点兜底
在 HTTPS 流量上有真实样本可用，不只能靠探测 authority 均值。

### P2 的一处调整

计划里 `health_min_samples_for_filter` 打算从 8 降到 4，实施时改成 **5**：
`HealthEwmaMinSamples` 默认就是 5，过滤门槛不该低于「分数被认为可信」的样本数，
否则等于用一个系统自己都不信的分数去拒绝节点。改 5 与 EWMA 对齐，语义一致。

**行为变化与兼容性**

- 健康池（可接受率 ≥60%）仍是两两比较，行为与 v1.3.0 一致；
  只有劣质池才会多抽候选。
- 两者都无延迟样本时，分数由「租约数」变为「(租约数+1)×400ms + 健康罚分」，
  量纲与其他候选一致；池内相对排序不变，但健康度开始真正参与比较。
- `PreferIdleIP` 策略不受冷启动延迟影响，仍只按租约计分。
- 无新增运行时配置项，无 schema 变更。

**设计取舍**

- 挂起**不进熔断状态机**：`CircuitOpenSince` / `FailureCount` 都不动，避免污染熔断的退避计数；
  节点只是暂时不参与选点。
- 阈值取 2 而不是 1：目标自身宕机（端口关闭、主机失联）会让任何节点都表现为零入向，
  单次证据不足以归咎节点。
- 三条成功路径都会清零，包括主动探测：挂起中的节点拿不到流量，只有探测能证明它恢复了。
- 信号通过可选接口上报，未实现该接口的记录器（含测试桩）行为不变。

## 5. 验证方案

**单测**
- 只有一方有延迟样本时，P2C 必须保留已知延迟，而不是双双归零。
- 未知延迟节点的分数必须低于（更差于）已测节点，但不得被过滤。
- 池子可接受率 50% 时宽度为 3，90% 时为 2。
- 零入向连续 2 次后 5 分钟内不被选中（P1-1）。

**线上灰度**
1. 先发 P0-1 + P0-2，观察 6 小时；
2. 首跳 ≥ 67% 后再上 P1-1；
3. 每步保留 `failover_*` / `health_*` 热更新回退能力。

**判定标准**：首跳 ≥ 67%、失败率 ≤ 5%、p99 ≤ 4.5s 连续 6 小时成立。

## 6. 不做的事

- 不改 CONNECT 隧道的重试语义（字节写出后重放有重复提交风险）。
- 不改租约与粘性语义，不动协议与配置结构。
- 不引入新依赖；配置全部向后兼容。
